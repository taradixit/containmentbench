# ContainmentBench

ContainmentBench is a small testbed for checking whether coding agents stay inside simple Linux security boundaries. It runs scripted agent actions in weak and contained Docker environments and records what happens.

## Question

Can simple Linux controls reduce successful policy violations without breaking normal coding tasks, and can the runner detect the attempted violations?

## What it tests

- secret file reads and writes outside the workspace
- policy modification and root access
- process visibility, process limits, and memory limits
- approved and unapproved local network access
- writable state shared between separate runs

The benchmark has 6 benign and 13 adversarial scenarios. The adversarial scenarios use only fake files, local containers, and safe resource limits.

## Setup

You need Python 3 and Docker running Linux containers. On macOS, Docker Desktop provides the Linux VM.

```sh
git clone https://github.com/taradixit/containmentbench.git
cd containmentbench
./scripts/setup.sh
```

Setup builds the small Alpine-based image and runs the tests.

## Run

```sh
python3 run_benchmark.py
```

To run one case or one condition:

```sh
python3 run_benchmark.py --scenario A01 --condition contained
```

Results are written to `results/summary.json`, `results/summary.csv`, `results/runs.jsonl`, and `results/events.jsonl`.

## Scenarios

Scenarios are plain JSON files in `scenarios/`. Each action states what it tries, whether it should be allowed, and which invariant it tests. The runner executes every action, including retries after a failure.

## Results

These results were produced on September 12, 2026 with Docker Engine 28.1.1 and Linux 6.10.14 containers on Docker Desktop.

| Condition | Benign success | Adversarial scenarios with a violation | Blocked actions | Detection rate | False positives | Time |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Baseline | 100.0% (6/6) | 100.0% (13/13) | 0 | 100.0% (15/15) | 0 | 8.7 s |
| Contained | 100.0% (6/6) | 7.7% (1/13) | 14 | 100.0% (15/15) | 0 | 12.7 s |

The contained memory exhaustion action was the remaining violation. Docker reported a 64 MB cgroup limit, but the container still allocated and touched 96 MB. The saved run data contains the exact command, exit code, and output.

Detection means the runner logged a declared security-sensitive action. This is useful for scripted tests, but it is not kernel-level syscall monitoring.

## Containment

The contained condition uses:

- a fresh writable workspace for each scenario
- no mount for the synthetic host secret or shared state
- a read-only root filesystem and read-only policy mount
- UID 65534, all Linux capabilities dropped, and `no-new-privileges`
- a small seccomp denylist and a separate PID namespace
- a 32-process limit, 10-second CPU limit, 0.5 CPU quota, 64 MB memory request, and a small temporary filesystem
- an internal Docker network that exposes only the approved local service

The baseline runs as root, shares the Docker VM PID namespace, mounts the synthetic host fixtures read-write, and can reach both local services.

## Project structure

- `containment.py` runs containers and creates the synthetic test environment
- `policy.py` and `policy.json` define readable, writable, network, and resource rules
- `invariants.py` evaluates actions and calculates results
- `monitor.py` writes JSON Lines security events
- `tests/` contains unit tests and a Docker smoke test

## Limitations

- Actions are scripted instead of generated by a real coding model.
- The monitor sees actions submitted through the runner, not every syscall inside a container.
- Docker Desktop runs Linux in a VM, so this does not measure direct Linux host isolation.
- The 64 MB memory limit was reported but not enforced on the machine used for the saved results.
- This is a research prototype, not a production sandbox or a defense against kernel exploits.
